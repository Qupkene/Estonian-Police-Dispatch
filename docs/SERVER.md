# EPD server: accounts, saves, self-hosted map, auto-update

The game stays a static single-page app. On the owner's MainServer it is served together with a
small PHP API (accounts, cloud saves, leaderboard, deploy webhook) and a self-hosted Estonian
vector map. Guests can still play without an account; their progress lives in the browser only.

This file is the shared contract between the backend, the frontend account code, the map and the
deploy scripts. Keep it in sync when something changes.

## 1. Repository layout

```
server/
  api/index.php        single router for every /api/* request
  lib/*.php            db, http helpers, auth, saves, scores, deploy hook
  dev-router.php       router for `php -S` during local development
deploy/
  mainserver/          installer, update script, systemd units, container Caddyfile, compose
  relee/               the block that adds politsei.eu to the relay VPS (generated by the installer)
src/net/               frontend API client and account store
```

## 2. Runtime layout on MainServer

| Path on host | Path in container | Mode | Content |
| --- | --- | --- | --- |
| /opt/stack/politsei/www | /app/www | ro | built frontend (`dist/`), plus `version.txt` (deployed commit) |
| /opt/stack/politsei/repo/server | /app/server | ro | PHP code from the repository |
| /opt/stack/politsei/data | /data | rw | `epd.sqlite`, `deploy-secret`, `control/` (update tickets) |
| /opt/stack/politsei/tiles | /srv/tiles | ro | `estonia.pmtiles` (Protomaps basemap extract of Estonia) |

Containers (`/opt/stack/politsei/compose.yml`):

- `relee-politsei`: `lscr.io/linuxserver/wireguard`, on the existing `veeb` network (so the existing
  DOCKER-USER isolation for that network applies), WireGuard address `10.99.0.5/32`, peer = relay
  `10.99.0.1` at `80.47.227.213:51820`.
- `politsei`: `dunglas/frankenphp:1-php8.4`, `network_mode: service:relee-politsei`, runs the
  Caddyfile from `deploy/mainserver/Caddyfile`, listens on :80 inside that network namespace.

Environment for `politsei`: `EPD_DATA=/data`, `EPD_TRUSTED_PROXY=10.99.0.1`.

Relay VPS: Caddy site `politsei.eu` (and `www.politsei.eu` redirecting to it) →
`reverse_proxy 10.99.0.5:80`. TLS is terminated on the relay. DNS: A records for `politsei.eu` and
`www.politsei.eu` → `80.47.227.213`.

## 3. HTTP routes (inside the container)

- `/api/*` → PHP, `/app/server/api/index.php` (the router reads the path itself).
- `/tiles/*` → static files from `/srv/tiles` with HTTP range support (PMTiles reads byte ranges).
- everything else → static from `/app/www`, unknown paths fall back to `/index.html`.
  `index.html` and `sw.js` get `Cache-Control: no-cache`, `/assets/*` get one-year immutable caching.

## 4. API

All bodies are JSON (`Content-Type: application/json`). Session cookie `EPDSESS` (HttpOnly,
SameSite=Lax, Secure when the request came over HTTPS via the relay). Every state-changing request
(POST, PUT, DELETE) must carry the header `X-EPD: 1`, otherwise 403 (simple CSRF guard).
Errors: `{ "error": "<code>", "message": "<Estonian text>" }` with a fitting status.

| Method | Path | Body | Response |
| --- | --- | --- | --- |
| GET | /api/health | | `{ ok: true, version: "<sha or dev>", accounts: true }` |
| GET | /api/me | | `{ user: { id, name, created } \| null }` |
| POST | /api/register | `{ name, password }` | `{ user }`; 400 invalid, 409 name taken, 429 too many |
| POST | /api/login | `{ name, password }` | `{ user }`; 401 wrong, 429 too many |
| POST | /api/logout | | `{ ok: true }` |
| DELETE | /api/me | `{ password }` | `{ ok: true }` (deletes the account and all its data) |
| GET | /api/save | | `{ career, settings, autosave, updated: { career?, settings?, autosave? } }` (null when missing, unix ms) |
| PUT | /api/save/{slot} | any JSON object | `{ ok: true, updated }`; slot is `career`, `settings` or `autosave`; 413 when too big |
| DELETE | /api/save/{slot} | | `{ ok: true }` |
| POST | /api/score | `{ regionId, mode, difficulty, score, grade, incidents, arrests, start }` | `{ ok: true, rank }` (logged-in users only) |
| GET | /api/scores?region=&limit= | | `{ scores: [{ name, score, grade, regionId, difficulty, incidents, at }] }` best per user |
| POST | /api/deploy-hook | GitHub webhook | 202 `{ queued: sha }` or 200 `{ ignored: reason }` |

Rules:

- Names: 3 to 24 characters, letters (including õäöüšž), digits, `_`, `.`, `-`; case-insensitive unique.
- Passwords: at least 8 characters, stored with `password_hash` (argon2id when available, else bcrypt).
- Login/register rate limit: 10 attempts per 15 minutes per IP and name, 40 per IP.
- Save size limits: `autosave` 4 MB, `career` and `settings` 512 kB.
- Scores: `score` 0 to 100, one row per finished shift, leaderboard shows each user's best.
- Client IP: `X-Forwarded-For` is trusted only when the direct peer is `EPD_TRUSTED_PROXY`.

## 5. Auto-update from GitHub

1. Push to `main` → GitHub Actions `CI` runs.
2. When the run finishes, GitHub sends a `workflow_run` webhook to `https://politsei.eu/api/deploy-hook`
   (secret = `/opt/stack/politsei/data/deploy-secret`, content type JSON, event "Workflow runs").
3. The API checks the HMAC (`X-Hub-Signature-256`), accepts only `action=completed`,
   `conclusion=success`, `head_branch=main`, `event=push`, workflow name `CI` and
   `head_repository.full_name=Qupkene/Estonian-Police-Dispatch`, and writes
   `/data/control/uuenda.json` = `{ sha, at, source: "webhook" }`.
4. On the host, `politsei-uuenda.path` sees the ticket and starts `politsei-uuenda.service`
   (`/usr/local/sbin/politsei-uuenda.sh`): it only ever deploys the current tip of `origin/main`
   (whatever the ticket says), fetches that commit, checks on the GitHub API that every
   check run of that commit succeeded, builds the frontend in a `node:22` container, copies the result
   into `www/` (contents, not the folder: bind mounts point to the inode), writes `version.txt`, checks
   `/api/health`, and restores the previous version if anything fails.
5. `politsei-uuenda.timer` runs the same script every 10 minutes as a fallback (compares the deployed
   commit with `git ls-remote origin main`), so a missed webhook only delays an update.
6. When `/etc/pidu.env` provides a Telegram token and chat id, the script reports the result there.
