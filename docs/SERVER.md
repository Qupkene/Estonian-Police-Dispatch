# EPD server: accounts, saves, self-hosted map, auto-update

The game stays a static single-page app. On the owner's MainServer it is served together with a
small PHP API (accounts, cloud saves, leaderboard, deploy webhook) and a self-hosted Estonian
vector map. Guests can still play without an account; their progress lives in the browser only.

This file is the shared contract between the backend, the frontend account code, the map and the
deploy scripts. Keep it in sync when something changes.

### 2.1 Map data (roads and buildings)

So that units drive along real roads and incidents sit at buildings, `scripts/build-mapdata.mjs`
derives two compact binary files from `estonia.pmtiles` (no external service):

- `roads-v1.bin`: the car road graph (highway, major and minor roads, living streets, service roads
  except parking aisles; no paths, tracks, rail or ferries), clipped to exact tile bounds, stitched
  across tile borders, degree-2 chains merged and simplified, one-way and a speed class per edge.
- `buildings-v1.bin`: area-weighted building centroids (40 m2 and up) with a size class and a grid
  index; a building cut by tile borders is merged by feature id.

Both formats (versioned, little-endian typed arrays) are documented at the top of the script and
read by `src/map/roadGraph.ts`. The script reads zoom 15 tile by tile (the only zoom with every
building), writes each file to a temporary name in the output folder and renames it, also writes
`.gz` copies, and exits 1 without touching existing files on any failure. Local:
`node scripts/build-mapdata.mjs public/tiles/estonia.pmtiles public/tiles/`.

On the server `politsei-uuenda.sh` builds them after a successful update when a file is missing,
older than `estonia.pmtiles`, or the script changed (stamp in `olek/kaardiandmed.txt`), in a
`node:22` container without network, with the tiles folder mounted read-write and
`estonia.pmtiles` read-only on top; `paigalda.sh` does the same after the map extract, and
`politsei-uuenda.sh --kaardiandmed [--joud]` does it by hand. A failure is logged and reported,
never fatal: the game update stays, the old files stay.

The client (`src/map/roads.ts`, worker `src/map/roadWorker.ts`) fetches both files lazily once per
page. When they are missing (404, an HTML fallback, a damaged file, a network error) the map shows
the engine's positions exactly as before. The simulation itself never uses this data: units still
travel the engine's straight path in the same time; the map draws them at the same fraction of a
road route (A*), and incident markers at the nearest building (120 m), a real place's most
prominent building (200 m) or the nearest road (300 m).

Relay VPS: Caddy site `politsei.eu` (and `www.politsei.eu` redirecting to it) →
`reverse_proxy 10.99.0.5:80`. TLS is terminated on the relay. DNS: A records for `politsei.eu` and
`www.politsei.eu` → `80.47.227.213`.

## 3. HTTP routes (inside the container)

- `/api/*` → PHP, `/app/server/api/index.php` (the router reads the path itself).
- `/mp/*` → the game server at `127.0.0.1:8790`: `GET /mp/health`, WebSocket `/mp/ws`. Not compressed,
  `no-store`; 502 while it is down (the client retries).
- `/tiles/*` → static files from `/srv/tiles` with HTTP range support (PMTiles reads byte ranges).
  No `encode` on this route: range replies must be `206` with `Content-Length`, `Accept-Ranges: bytes`
  and a stable `ETag`/`Last-Modified`. `*.bin` (map data, section 2.1) is served as
  `application/octet-stream` with `file_server { precompressed gzip }`, so the `.gz` copy goes out
  with `Content-Encoding: gzip`; a missing file is a plain 404. One day of caching for both.
- `/admin` → 308 to `/admin/`; `/admin/*` → static from `/app/www/admin` (the admin panel, section 4.2):
  `no-store` (its hashed `/admin/assets/*` a year, immutable), `X-Robots-Tag: noindex, nofollow`, a missing file
  is 404, never the game's index. The service worker leaves `/admin` and `/admin/*` alone.
- everything else → static from `/app/www`, unknown paths fall back to `/index.html`.
  `index.html` and `sw.js` get `Cache-Control: no-cache`, `/assets/*` get one-year immutable caching.

## 4. API

All bodies are JSON (`Content-Type: application/json`). Session cookie `EPDSESS` (HttpOnly,
SameSite=Lax, Secure when the request came over HTTPS via the relay). Every state-changing request
(POST, PUT, PATCH, DELETE) must carry the header `X-EPD: 1`, otherwise 403 (simple CSRF guard).
A logged-in client also sends `X-EPD-User: <its account id>`; routes that need a login answer
409 `user_mismatch` when the session cookie belongs to another account (see 4.1).
Errors: `{ "error": "<code>", "message": "<Estonian text>" }` with a fitting status.

Rules:

- Names: 3 to 24 characters, Latin letters (including õäöüšž), digits, `_`, `.`, `-`; case-insensitive unique.
- Passwords: at least 8 characters, stored with `password_hash` (argon2id when available, else bcrypt).
- Login/register rate limit: 10 attempts per 15 minutes per IP and name, 40 per IP.
- Save size limits: `autosave` 4 MB, `career` and `settings` 512 kB.
- Scores: `score` 0 to 100, `incidents` at least 1 (400 `empty_shift` otherwise), one row per finished shift, leaderboard shows each user's best.
- Client IP: `X-Forwarded-For` is trusted only when the direct peer is `EPD_TRUSTED_PROXY`.
- Speech: uncached synthesis 150 per 10 minutes per IP, cache hits are free.

### 4.1 API details (as implemented in `server/`)

These refine the table above.

General:

- Every reply is JSON with `Content-Type: application/json; charset=utf-8` and `Cache-Control: no-store`.
- Unknown path: 404 `not_found`. Known path, wrong method: 405 `method_not_allowed` with an `Allow` header.
  Missing `X-EPD: 1` on POST/PUT/DELETE (except `/api/deploy-hook`): 403 `csrf`. Uncaught failure:
  500 `server_error` (logged with `error_log`, no details in the reply).
- Small JSON endpoints (register, login, logout, score, daily, rooms, DELETE /api/me) accept at most 64 kB, else
  413 `too_large`. A body that is not a JSON object: 400 `bad_json`. An empty body counts as `{}`.
- Validation errors may carry `field` (the offending body field), e.g.
  `{ "error": "invalid_score", "message": "Vigane väli: score.", "field": "score" }`.
- All times are unix milliseconds.

Accounts and sessions:

- `POST /api/register` also logs the new account in (same cookie as login). Status 200.
- Names are trimmed. Allowed characters exactly: `A-Z a-z õäöüšž ÕÄÖÜŠŽ 0-9 _ . -` (other alphabets are
  rejected, so look-alike names cannot impersonate others on the leaderboard). Uniqueness uses
  `mb_strtolower`, so `Õnne` and `õnne` are the same name. With the intl extension, names are
  normalised to NFC first; without it a decomposed `õ` (o + combining tilde) is simply rejected.
- Passwords: 8 to 256 characters.
- Codes: 400 `invalid_name` / `invalid_password`, 409 `name_taken`, 401 `bad_login` (same reply for an
  unknown name and a wrong password), 429 `rate_limited` with `Retry-After: 900`.
- Rate limit bookkeeping (table `login_attempts`): every register attempt counts (successful ones too,
  which also caps account creation per IP), every failed login counts, a failed password check on
  `DELETE /api/me` counts. A successful login clears that IP and name's failed logins. The check runs
  before the password, so a blocked IP gets 429 even with the right password.
- `DELETE /api/me`: 401 `auth_required` when not logged in, 400 `password_required` without a password,
  403 `wrong_password` for a wrong one (the session stays valid).
- `X-EPD-User`: every route that needs a login (saves, `POST /api/score`, `POST /api/daily`, the room routes, `DELETE /api/me`) compares the
  header, when sent, with the session's account and answers 409 `user_mismatch` when they differ. The
  cookie is shared by all tabs of a browser, so after another tab logged in as someone else, a tab that
  still syncs the first account cannot write into the second one. Without the header nothing is checked.
  The client treats `user_mismatch` like 401: that tab stops syncing and asks to log in again.
- Session cookie `EPDSESS`, `Path=/`, 30 day idle expiry: the cookie and the server-side stamp are
  refreshed at most once an hour while the player is active. Session files live in `EPD_DATA/sessions`.
  Guests never get a session cookie; an unknown or expired cookie is cleared. A new session id is issued
  on every login and register.
- Session generation (schema step 10, `users.sess_gen`, default 0): a session remembers the generation it was
  made in (`gen`, absent for 0, so every older session file stays valid). An admin's password reset, "log out
  everywhere" or block raises it, and every older session of that account ends at its next request. A blocked
  account (`users.disabled = 1`) has no session at all; its login with the right password answers 403
  `account_disabled` (a wrong one 401 `bad_login` as always, so the block is not revealed).

Saves:

- All save routes need a login: 401 `auth_required`.
- Versions: every write of a slot stores `updated` = server time in unix ms, but always at least the
  previous version + 1, so versions of a slot strictly grow (two writes in one millisecond differ).
- `GET /api/save`: `updated` only has keys for slots that exist, e.g.
  `{ "career": {...}, "settings": null, "autosave": null, "updated": { "career": 1760000000000 } }`.
  Slot contents come back byte for byte as they were stored. A deleted slot comes back as `null` with
  its version in `updated` (the deletion marker). `?versions=1` answers only `{ "updated": {...} }`.
- `PUT /api/save/{slot}`: 400 `bad_slot` (unknown slot), 400 `not_object` (not starting with `{`),
  400 `bad_json` (invalid JSON), 413 `too_large`. The reply's `updated` is the slot's new version.
- `DELETE /api/save/{slot}` does not remove the row: it stores the JSON `null` with a new version and
  answers `{ ok: true, updated }`, so other devices learn about the deletion instead of uploading their
  old copy again. Deleting a missing slot is fine (it gets a marker too).
- `?base=<version>` on PUT and DELETE: the version the client's copy builds on (`0` = "the server has no
  such slot"). The write only happens when the stored version (0 for a missing row) still equals it,
  else 409 `save_conflict` with `updated` = the stored version, and nothing is written. Check and write
  run in one `BEGIN IMMEDIATE` transaction. Without `base` the write is unconditional (older clients).
  400 `bad_base` when `base` is not a plain non-negative integer.

Cloud sync in the client (`src/net/account.ts`, decisions in `src/net/sync.ts`, browser data per identity in
`src/store/space.ts`):

- Account data and guest data never mix in the browser. The guest keeps the plain keys (`epd:career`,
  `epd:settings`, `epd:autosave`, `epd:sync`, `epd:backup.*`); every account has a cache namespace
  `epd:acct:<id>:career`, `:settings`, `:autosave`, `:sync`, `:backup.*`. The server is the source of truth:
  the cache only makes sign-in fast and keeps changes made while the server was out of reach until they are
  uploaded. Exactly one namespace is active and the stores read and write only that one.
- Sign-in makes the account's namespace active (the cache first, then the merge with `GET /api/save` below).
  The guest's data stays untouched. On the first sign-in of an account in a browser, the guest's career and
  shift fill the slots the account never had on the server, as a copy (the guest keeps its own), and an account
  new to the browser starts with the guest's settings until its cloud copy replaces them.
- Sign-out uploads what is waiting (at most 3 s), then the guest's own data is active again: the menu never
  shows the account's career or shift to a guest. The sign-out dialog's "Kustuta selle konto andmed sellest
  brauserist" (on by default) then removes the account's namespace, except slots the server does not have yet
  (they stay with their marker entries and the next sign-in uploads them). The same switch to the guest's data
  happens when the session ends elsewhere (401, `user_mismatch`, another tab signing out or in as someone
  else; a shift still running is saved into the account's namespace first and the game returns to the login
  screen) and after `DELETE /api/me` (which also removes the account's namespace).
- No clock is compared with the server's. Per slot, the namespace's marker (`epd:acct:<id>:sync`) keeps the
  account the data was last synced with (`owner`), the server version it was last synced with (`base`) and
  whether it changed in this browser since (`dirty`). Format 3: `{ v: 3, slots: { career: { owner, base,
  dirty }, ... } }`. The guest's `epd:sync` has the same form plus `account`, the account this browser is
  signed in to (read by the other tabs), and the format 1 fields `owner`/`updated` for a rollback to 92ed7f5
  (`legacyMeta`: while signed in, and signed out once an account was signed in here, `owner` is 0, so 92ed7f5
  never uploads the guest's data over the account's cloud copy). A guest marker of format 1 or 2 (from before
  namespaces) is read once on load, and keeps its format until that move succeeds: slots whose
  owner is an account move into that account's namespace with their entries (changes not uploaded yet stay
  marked and go up at the next sign-in), the guest gets back what an account's cloud copy once replaced
  (`epd:backup.<slot>` entries with `owner: null`, or `epd:backup.career.guest`), and data without an owner
  stays the guest's. Format 1 entries are read as "changed on top of that version".
- On login and whenever the tab becomes visible or gets focus (a `?versions=1` check first, the full read
  only when a version moved), the client reads the cloud and decides per slot: the server still has
  `base` → upload when dirty; the server has a newer version → take it; the server's version is older
  than `base` (row gone, or a restored database) → upload. Guest data, or data last synced with another
  account, never overwrites a cloud slot: it only fills slots that are empty or deleted.
- Uploads send `?base=`; on 409 `save_conflict` the tab reads the cloud again instead of overwriting.
  When both sides changed, the cloud copy wins.
- Cache data that a cloud copy replaces while it exists nowhere else (unsynced changes) is first copied to
  `epd:acct:<id>:backup.<slot>` as `{ at, owner, data }`.
- A tab stops syncing when another tab of the browser signs in to another account, signs out or clears
  the data (a `storage` event on `epd:sync`), or when the server answers `user_mismatch`.
- Choosing a guest, e-ID or 2024 login ends an open session (the guest's data becomes active at once) and
  keeps a late `/api/me` answer from starting one. "Delete all data" in Settings signs out (after the last
  uploads) before it clears the browser, so the reload does not pull the cloud data back.
- Scores: only a shift played signed in to an account posts `POST /api/score`; guests never post.

Leaderboard:

- `POST /api/score`: `regionId` in `pohja | ida | louna | laane`, `mode` in `career | free`,
  `difficulty` in `cadet | normal | veteran | realistic`, `grade` in `S A B C D F`, `score` a number
  0 to 100 (stored rounded), `incidents` and `arrests` 0 to 100000, `start` a non-negative number
  (shift start, unix ms). Errors: 401 `auth_required`, 400 `invalid_score` with `field`,
  400 `unranked_mode` for `director` and `tutorial` shifts (they never reach the leaderboard).
- `rank` is the place this shift's score takes on its region's board: 1 + the number of other players
  whose best score in that region is strictly higher.
- `GET /api/scores`: public. `region` empty or missing = all regions, unknown region = 400 `bad_region`.
  `limit` defaults to 20 and is clamped to 1..50. Sorted by score, ties go to the earlier `at` (when the
  shift was submitted).

Daily challenge, Päeva väljakutse (`server/lib/daily.php`, client `src/sim/daily.ts`, `src/net/daily.ts`):

- Every day has one shift, the same for everyone. The client builds it from the date alone
  (`dailyChallenge('YYYY-MM-DD')`): one starter sector (docs/SECTORS.md; every starter sector comes up once
  in each run of N consecutive days, N = their number, in a shuffled order without the same sector on two
  days in a row; the four whole prefectures while there is no sector data), a start in the morning,
  afternoon, evening or night (Friday and Saturday nights more often), weather from the season (harsh
  now and then), difficulty `normal`, 3 game hours, mode `free`, `fixedSchedule` and a seed from the date.
  The date is the calendar day in Europe/Tallinn; a new challenge opens at midnight there. A daily run is
  a free shift with `sim.flags.daily = 'YYYY-MM-DD'` (and `flags.dailyStarted`, the real start in unix ms).
- Daily runs never go to `POST /api/score` or the normal leaderboard; the report posts them once to
  `POST /api/daily` (only when played signed in to an account, like scores). Guests can play; their result
  stays in the browser (`epd:daily.guest`, the first one of the day) and never counts.
- `POST /api/daily`: 401 `auth_required` without a session, 409 `user_mismatch` as for scores. Body fields
  as for `POST /api/score` (`regionId`, `score` 0 to 100, `grade`, `incidents` at least 1 else 400
  `empty_shift`, `arrests`), plus `day` (a real date `YYYY-MM-DD`), `sector` (a sector id or `''` for a whole
  prefecture) and optional `started` (unix ms, the real time the run was started); invalid fields give
  400 `invalid_score` with `field`. Rate limits are those of `POST /api/score` (a login is required; there
  is no extra per-request limit, and only one row per player and day is ever stored).
- `day` must be today in Tallinn, or yesterday when `started` lies before midnight (within yesterday) and
  the run arrives within 4 hours after midnight; otherwise 400 `day_closed` (field `day`). A `started` more
  than 10 minutes in the future is 400 `invalid_score`.
- The first run of a player and day is stored (table `daily_scores`, schema step 3, `UNIQUE (user_id, day)`)
  and answers `counted: true`; every later one answers `counted: false` and changes nothing (a replay is
  practice). `rank` is the place of the player's counted run: 1 + the number of players with a strictly
  higher score that day; `players` is the number of players with a counted run that day.
- `GET /api/daily?day=`: public. `day` missing or empty = today in Tallinn; not a real date = 400 `bad_day`.
  `scores` is the top 50 sorted by score, ties to the earlier `at` (when the run was submitted), each with
  its `rank` (same rule as above, so equal scores share a place). `me` is the caller's counted run with its
  rank when signed in (else `null`), also when it is not in the top 50.
- Deleting an account deletes its daily rows too.
- `EPD_TEST_CLOCK=1` lets `X-EPD-Test-Now: <unix ms>` set the clock of the day rules, but only under PHP's
  built-in server (`tests/server.test.ts`); FrankenPHP ignores it.

Multiplayer rooms, Mitmikmäng (`server/lib/rooms.php`, client `src/net/rooms.ts`, `src/sim/room.ts`; design in
docs/MULTIPLAYER.md):

- Every route needs a login (401 `auth_required`, 409 `user_mismatch` as for scores). A room the caller is not
  in answers 404 `room_not_found`, the same as a missing code.
- Codes: 6 characters from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`; routes take them in any case (`/api/rooms/k7m2qx`),
  `join` also accepts spaces and dashes. Unknown, closed or malformed codes count against the IP: 30 in 10
  minutes, then 429 `rate_limited` (`rate_events`, bucket `room_miss`).
- `POST /api/rooms`: `mode` `race` (default), `role` (role co-op) or `sector` (sector co-op),
  `regionId`, `sector` (`''` for the whole prefecture, else `<regionId>-<name>`), `difficulty`, `hours` (2, 3, 4
  or 6, an integer), `slot` (`morning | afternoon | evening | night`); a `sector` room also needs `desks`: a list
  of 2 to 4 distinct sector ids of the prefecture (`<regionId>-<name>`; that they neighbour each other is the
  client's check), and its `sector` becomes the first desk. Invalid fields give 400 `invalid_room` with
  `field`. 20 new rooms per IP and hour (`room_create`), else 429. The server draws the seed and the code.
- A player is in one open room (`lobby` or `running`, or `finished` between two rounds) at a time: creating or joining
  another leaves the others. Joining a room one is already in (also after leaving a running one) is coming back, not a
  second seat. A full room (4) answers 409 `room_full`, a running one 409 `room_started` to anyone not already in it; a
  room between two rounds takes new players (they are in the next round).
- The room (`room`): `{ code, mode, state, round, last, v, host, me, max, options: { regionId, sector, difficulty,
  hours, slot }, seed, day, created, started, players: [{ id, name, seat, host, ready, online, left, done, role }],
  results: [{ id, name, score, grade, incidents, arrests, xp, at, rank }] }`. `role` is the co-op desk the player
  picked, or the seat's default (`dispatch`, `calls`, `radio`, `dispatch` for seats 0 to 3). A `sector` room adds
  `options.desks` and each player's `desk`: the one they picked if the room still has it, else
  `desks[seat % desks.length]`. `seed` and `day` (the start day in Tallinn) are `null`
  until the start. `host` and `me` are account ids. `rank` is 1 + the number of strictly higher scores. `ready` is
  the lobby's ready mark (the host always is); once the round is on it says who takes part in it (was ready at the
  start). `round` counts the room's rounds (1 for a new room); `results` are the current round's, and `last` is the
  round before: `{ round, mode, seed, results }`, or `null` in the first round (or when nobody's result of it is kept).
- `v` = `<revision>.<online seat mask>`. The revision grows on every change; `online` = polled within 20 s. A
  poll writes the caller's `seen` at most every 5 s. With `?v=` equal to the current tag the answer is
  `{ v, unchanged: true }`.
- `PUT /api/rooms/{code}` (host, lobby; 403 `not_host`, 409 `room_started`) replaces the options and clears the
  other players' ready marks. `mode` (optional, the room's own when missing) switches the mode: `race`, `role` or
  `sector` (400 `invalid_room` `field: mode`, 400 `mode_unavailable` for a mode not offered; a sector room needs
  `desks` as at the creation), and a mode change clears the players' drafts. `ready` must be a boolean. `start`: 403 `not_host`, 409 `too_few` (fewer than 2 players take
  part), 409 `not_ready`, 409 `room_started`; sets `running`, `started` and `day`. Taking part: the host, every
  player ready, and every player here (polled within 20 s); somebody here and not ready answers `not_ready`,
  somebody away does not count (they stay in the room and may still play the round, which does not wait for them).
- `leave`: in the lobby the seat is freed; in a running room, or one between two rounds, the player stays listed with
  `left: true` and can no longer send a result (409 `left_room`). The host's role passes to the earliest-joined player
  still in. A lobby nobody is left in becomes `closed`, a running room `finished`. In the lobby the host's role also
  passes, to the earliest-joined player who is online, when the host has not polled for 5 minutes (the old host is no
  longer ready).
- `result`: fields and limits as for `POST /api/score` (`score` 0 to 100, `grade`, `incidents` at least 1 else
  400 `empty_shift`, `arrests`); 409 `not_started` in the lobby, 409 `room_closed` for a closed room or one
  finished over 12 hours ago. `seed` (optional, 0 to 2^32 - 1) is the shift's: when it is not the room's current
  round's, 409 `round_over` (a result of a round the host ended, or of an earlier one). The first result of a player
  counts (`counted: true`), later ones answer `counted: false`. Once every player still in who takes part in the round
  has a result the room is `finished`.
- `reopen` (rounds, docs/MULTIPLAYER.md section 11) `{ round?, end? }`: a member still in the room comes back after a
  round (409 `left_room` after leaving it, 409 `room_closed` for a closed room; 400 `invalid_room` with `field` for a
  `round` that is not a positive integer or an `end` that is not a boolean). A `finished` room opens for its next round,
  whoever comes back first; a `running` one changes only with `end: true` from the host (403 `not_host` for the
  others), which ends the round for everybody; a lobby and a `round` other than the room's change nothing. The next
  round: the results move to `room_round_results` (with the round, mode and seed) and become `last`, players who left
  go, the others stay not ready (the host is), `round` grows, a new seed is drawn, `started`, `engine`, the co-op
  clock, digests, log and snapshot are cleared, a sector room's joined force is again `{ crews: [] }`. Options, mode,
  roles, desks and drafts stay. Counts as a poll (`seen`).
- `GET /api/rooms` also answers a room between two rounds (`finished`) the caller is still in when its round started in
  the last 12 hours; an open room comes first.
- Time rules, applied on every read and write: a lobby nobody polled for 30 minutes becomes `closed`, a running
  room is `finished` 12 hours after its start. Rooms nobody changed for 30 days (`updated`) are deleted with their rows
  (swept on `POST /api/rooms`). Tables `rooms`, `room_players`, `room_results` (schema step 4); schema step 11
  (additive): `rooms.round` (default 1) and `room_round_results` (room, round, user, mode, seed, score, grade,
  incidents, arrests, xp, at; key room, round and user; it goes with the room and with the account).
- Custom force (2.26.0, `src/sim/custom.ts`): the options may carry `custom: { crews: [[type, station, officer...]...],
  budget?: true }`, at most 40 crews of the known unit types, a station id of the room's prefecture, at most 6 distinct
  officer indices 0..59 (the prefecture's draft pool) per crew, each officer once (400 `invalid_room`, field `custom`).
  Stored as compact JSON in `rooms.custom` (schema step 8, default `''` for the standard roster) and returned in
  `options.custom` and in the game server's ticket. The clients and the game server clean it the same way when they
  build the shift. The WebSocket frame limit of the game server is 16 KiB so the ticket of the largest force fits.
  An empty `crews` list in a race or sector room means custom forces on: `POST /api/rooms/{code}/custom
  { custom }` stores a member's own draft in `room_players.custom` (schema step 9) while the room is in the lobby
  (409 `not_custom` in a role room or with custom forces off, 409 `officer_taken` with `officer` when another
  player of the room drafted one of the officers). The room JSON shows each player's `custom`. A sector room's start
  joins the drafts in seat order into `rooms.custom` (at most 100 crews). A change of prefecture, or custom forces
  off, clears the drafts.
- Room results never go to `/api/score`, `/api/daily` or their boards. Deleting an account removes its seats and
  results (earlier rounds' too) and passes on the host role (`epd_rooms_forget_user`, in the deletion's transaction).
- The clock of the room rules is the daily challenge's: `X-EPD-Test-Now` works under `EPD_TEST_CLOCK=1` with
  PHP's built-in server only.

Co-op rooms, Ühisvahetus (`server/lib/coop.php`, client `src/net/coop.ts`, `src/store/coop.ts`, `src/sim/coop.ts`;
design and protocol in docs/MULTIPLAYER.md section 4):

- Modes `role` and `sector`. `POST /api/rooms/{code}/role` `{ role }` (`calls | dispatch | radio`, else 400
  `invalid_room` `field: role`) in the lobby only (409 `room_started`); a race room answers 409 `not_coop` on every
  co-op route. `POST /api/rooms/{code}/desk` `{ desk }`: one of a sector room's desks (else 400 `invalid_room`
  `field: desk`), lobby only (409 `room_started`), 409 `not_sector` in a role room.
- `start` writes the log's first command at turn 0: `{ k: 'setup', s: -1, a: [hostSeat, [[seat, role, name],
  ...]] }`; in a sector room the rows are `[seat, desk, name]`.
- The clock: turn = `floor((now - started) / turn_ms)`, `turn_ms` 1000. A command posted at turn T is stamped
  `T + input_delay` (2). Ids grow; within a turn commands apply in id order. Seat -1 is the server's own commands
  (`setup`, `left`, `back`, `host`); players cannot post those kinds.
- `POST /cmd`: running room (409 `not_running`), still in it (409 `left_room`). Body at most 4 kB (413), 1 to 20
  commands (400 `invalid_command` with `field`, 400 `too_many_commands`). Kinds and argument shapes: `ack [id]`,
  `prio [id, 1..4]`, `send [id, [id x 1..12]]`, `recall [id]`, `close [id, word, word?]`, `agency [id, word]`,
  `pursuit [id, word]`, `reply [id, word]`, `break [id, 0|1]`, `check [id, ref, ref]`, `answer [id]`, `ask [id,
  word]`, `interp [id]`, `endcall [id, word, 0..4, word or '']`, `q [word, text <= 64]`, `ping [text <= 140]`,
  `speed [0..4]`, `end []`, and for sector rooms `lend [id, id]` (an incident and a crew) and `lendans [1..1000000,
  0|1]` (a lend request's id and the answer). Ids match `[A-Za-z0-9_-]{1,40}`, words `[a-z_]{1,24}`, refs are a person id or a
  plate (letters, digits, space, `_.-`, at most 40), texts have no control characters. `speed` and `end` are the
  host's (403 `not_host`). The meaning and the role permissions are checked by every client's sim, identically.
  Batches per player: a bucket of 4, refilled at 2 a second (429 `rate_limited`, `Retry-After: 1`). At most
  20 000 commands per room (409 `log_full`).
- `GET /log`: `after` the last id the client holds (max 500 commands per answer, `more: true` when there are
  others). `h=<turn>:<16 hex>` reports the client's state digest; `ack=1` says it has just resynced. The host's
  digests are kept (the last 8, `rooms.ref_hashes`); a client's digest that differs from the host's of the same
  turn sets its `resync` (true in its answers until `ack=1`) and asks the host for a snapshot (`snapReq: true` in
  the host's answers). `snap` is the latest snapshot's turn. A poll is a read unless something changed: `seen`
  every 5 s, a digest every 10 turns, seats leaving or returning.
- Seats: a player still in the room who has not polled the log (or the room) for 60 s, or who left, is sequenced
  `left [seat]` (`room_players.away`); polling again or joining back sequences `back [seat]`. The host's role
  passes to the earliest-joined player still connected, announced as `host [seat]` (and `rooms.host_id` changes);
  the new host is asked for a snapshot at once.
- Snapshots: `PUT ?turn=&cmd=` from the host only (403 `not_host`): the shift state at the end of `turn` (at most
  the server's turn + 1), holding every command up to id `cmd` (at most the log's last id), gzip (starts with
  `1f 8b`, else 400 `not_gzip`), at most 2 MB (413), one row per room (`room_snapshots`, upserted), at most one
  per 10 s unless asked for (429). `GET` returns the bytes as stored.
- A running co-op room nobody polled for 15 minutes is `finished`. When a room finishes or closes its commands
  and snapshot are deleted (`epd_coop_forget_room`), and so with rooms older than 30 days.
- Account deletion in a running co-op room: the seat is sequenced `left`, the host is asked for a fresh snapshot,
  then the account's commands (`room_commands.user_id`) and uploaded snapshots go with its seats and results.
- `result` takes an optional `xp` (0 to 100 000): every co-op player sends the team's result with their own XP.
- On the game server (docs/MULTIPLAYER.md section 9, `server/lib/mp.php`): when `EPD_MP=1` and
  `EPD_MP_URL/mp/health` answers `ok` and `secret: true` within a second, `start` marks a co-op room
  `engine = 'server'` (schema step 7, `rooms.engine`, default `''`; the room JSON has `engine`). The setup command is
  still logged, but the log, digests and snapshots are not used, and the seats are not sequenced by PHP.
  `POST /api/rooms/{code}/ticket` gives a member an entry ticket: `{ ticket, url: '/mp/ws', exp }`. The ticket is
  `base64url(json).base64url(hmac-sha256(first part, secret))` with `{ v: 1, code, user, seat, name, exp (now + 60 s),
  room: { code, mode, seed, day, options, started, setup: [hostSeat, rows] } }`; the secret is
  `EPD_DATA/mp/secret` (64 hex digits, mode 0600, created on first use). 409 `not_server_room` for a race room or a
  lockstep room, 409 `not_running`, 409 `left_room`, 404 for strangers. A ticket counts as being here (`seen`).
- Tables (schema step 5, additive): `room_commands` (index `(room_id, id)`), `room_snapshots`; columns `rooms.turn_ms`,
  `input_delay`, `host_seat`, `cmd_count`, `ref_hashes`, `snap_req`; `room_players.role`, `away`, `hash_turn`,
  `hash`, `resync`, `cmd_tokens`, `cmd_at`; `room_results.xp`. Every new column has a default. Schema step 6
  (additive): `rooms.desks` (a sector room's desks, comma separated, `''` otherwise) and `room_players.desk`.

Speech (`POST /api/tts`, `server/lib/tts.php`):

- The only route that does not answer JSON on success: `200 audio/wav`, `Cache-Control: private,
  max-age=604800`, `X-EPD-TTS: hit` or `miss`. Errors are JSON as everywhere. Needs `X-EPD: 1`.
- Body (at most 16 kB): `text` 1 to 400 characters after removing control characters, collapsing
  whitespace and trimming (NFC with intl), else 400 `invalid_text`; `voice` one of the TartuNLP v2
  speakers `mari tambet kalev liivika külli meelis albert indrek vesta peeter` (case-insensitive,
  `kylli` accepted for `külli`), else 400 `invalid_voice`; `speed` a number 0.75 to 1.35 (default 1,
  rounded to 0.01), else 400 `invalid_speed`. All with `field`.
- Cache: `EPD_DATA/tts/<first 2 hex>/<sha256(voice|speed with 2 decimals|text)>.wav`, written to a
  temporary file in the same directory and renamed. A per-clip lock file (removed afterwards) makes
  identical concurrent requests call the upstream once. Hits older than a day get a fresh mtime. About
  1 % of requests check the size: over 300 MB (`EPD_TTS_CACHE_MB`) the oldest clips by mtime are
  deleted down to 80 %, plus temporary and lock files older than an hour.
- Upstream: `EPD_TTS_UPSTREAM`, default `http://10.99.0.1/text-to-speech/v2` (the relay's Caddy
  forwards `/text-to-speech/*` to `https://api.tartunlp.ai`, `deploy/relee/lisa-tts.sh`; the container
  has no other way out). `off` switches synthesis off (useful for `php -S` without the relay). Request:
  POST JSON `{ text, speaker, speed }` with PHP streams (no curl), 12 s connect and read timeout,
  at most 4 upstream calls at a time (`tts_busy` 503 after 3 s of waiting). The reply counts only with
  status 200 and a RIFF/WAVE body of at most 8 MB.
- Failures: an unreachable upstream, another status or a body that is not WAV gives 503
  `tts_unavailable` (`Retry-After: 60`) and touches `EPD_DATA/tts/.down`; for 60 s every uncached
  request answers the same at once, without calling the upstream. A success removes the marker.
- Rate limit: only requests that call the upstream count, 150 per IP per 10 minutes (`EPD_TTS_LIMIT`
  overrides the count), else 429 `rate_limited` with `Retry-After: 60`. Table `rate_events`
  (schema step 2), apart from `login_attempts`, so speech never counts against logins.
- The client (`src/audio/neurokone.ts`, `src/audio/ttsText.ts`) expands abbreviations, personal codes,
  plates and callsigns before sending, picks the voice (dispatcher mari, Häirekeskus vesta, each unit a
  stable voice of its crew leader's gender), plays one clip at a time through Web Audio with a radio
  filter, and after a 503, network error or timeout pauses the server voice for 1 minute (doubling up
  to 10) and uses the browser's Estonian voice, if any, meanwhile.

Deploy hook and health:

- `POST /api/deploy-hook` order of checks: 503 `not_configured` (no `EPD_DATA/deploy-secret`),
  413 `too_large` (body over 1 MB), 401 `bad_signature`, then the event. `ping` gives 200 `{ pong: true }`,
  other events and non-matching runs give 200 `{ ignored: "<field>=<value>" }` (e.g. `conclusion=failure`),
  a signed `workflow_run` with broken JSON gives 400 `bad_json`.
- The ticket is written as `control/.uuenda.json.<random>.tmp` and renamed to `control/uuenda.json`
  (same directory, so the rename is atomic). `at` is unix ms.
- `GET /api/health` also opens the database (and applies pending migrations), so a broken data volume
  answers 500 there. `version` is the trimmed content of `/app/www/version.txt` (dev: `../www/version.txt`
  next to the repository) when it looks like a version, else `"dev"`.
- Without `EPD_DATA` (local development) data goes to `data-dev/` in the repository, which gets its own
  `.gitignore`.
- `EPD_FAST_HASH=1` makes password hashing cheap, but only under PHP's built-in server (`php -S`, used by
  `tests/server.test.ts`). FrankenPHP ignores it, so production always uses PHP's default argon2id cost.

### 4.2 Admin panel (`/admin/`, `server/lib/admin.php`)

Who: an account with `users.role = 'admin'` (schema step 10, default `''`). The role is never given over the
web by default: the first admin is made on the server, then admins can make others in the panel.

```
sudo docker exec -it politsei php /app/server/bin/admin.php                lists the admins, asks for the name
sudo docker exec -it politsei php /app/server/bin/admin.php nimekiri       lists the admins
sudo docker exec -it politsei php /app/server/bin/admin.php lisa NIMI      makes NIMI an admin (and unblocks it)
sudo docker exec -it politsei php /app/server/bin/admin.php eemalda NIMI   takes the role away
sudo docker exec -it politsei php /app/server/bin/admin.php parool NIMI    a generated password, shown once; every
                                                                           session ends, the block and the login
                                                                           limit go
```

The account must exist (registered in the game). The command line's changes are logged as admin `server`, IP
`cli`. The script refuses to run outside the command line.

Access: every `/api/admin/*` route needs a logged-in admin (401 `auth_required`, 403 `not_admin`), and every
route but `me`, `unlock` and `lock` also needs the panel unlocked in this session: the admin's password again
(`POST /api/admin/unlock`), good for two hours (403 `admin_locked` otherwise). So a game cookie alone opens
nothing. Unlocking issues a new session id; wrong passwords count in the login limit (kind `admin`). Writes need
`X-EPD: 1` like the rest of the API. The page logs in with the game's own `/api/login` and unlocks with the same
password at once.

Guards: no admin deletes, blocks or demotes themselves (409 `self`), the last admin stays (409 `last_admin`).
An admin's own password change keeps their current session (the others end).

Log: every write goes into `admin_log` (schema step 10: `at`, `admin_id`, `admin_name`, `action`, `target`,
`detail` JSON, `ip`), also a failed unlock (`unlock_failed`). `target` is the account touched (`user:12`), else the
room (`room:ABC234`) or the backup's file name. Rows stay when the account is deleted; the panel cannot change
them. Passwords never go into the log.

One a minute (429 `too_soon`), 507 `disk_full` when less than two database sizes plus 100 MB are free |

Results follow the game's rules: `score` 0 to 100, the enums of `POST /api/score` (400 `invalid_score` with
`field`), a daily `day` as a real `YYYY-MM-DD`. Director and tutorial results can be stored but the public
leaderboard never shows them. Query numbers out of range: 400 `invalid_query`. Unknown ids: 404 `user_not_found`,
`score_not_found`, `daily_not_found`, `room_not_found`, `result_not_found`.

The page (`src/admin/`, Estonian): Ülevaade (the stats), Kontod (search, sort, a new account; one account with
every action, its results, daily runs, saves to read, edit, download, upload or delete, rooms and log),
Edetabel, Päeva väljakutse, Ruumid, Logi, Varukoopiad. An admin's game menu (the account chip) links to it.

## 5. Auto-update from GitHub

1. Push to `main` → GitHub Actions `CI` runs.
2. When the run finishes, GitHub sends a `workflow_run` webhook to `https://politsei.eu/api/deploy-hook`
   (secret = `/opt/stack/politsei/data/deploy-secret`, content type JSON, event "Workflow runs").
3. The API checks the HMAC (`X-Hub-Signature-256`), accepts only `action=completed`,
   `conclusion=success`, `head_branch=main`, `event=push`, workflow name `CI` and
   `head_repository.full_name=Qupkene/Estonian-Police-Dispatch`, and writes
   `/data/control/uuenda.json` = `{ sha, at, source: "webhook" }` (`at` in unix ms, written atomically
   via a temp file and rename in the same directory, see 4.1).
4. On the host, `politsei-uuenda.path` sees the ticket and starts `politsei-uuenda.service`
   (`/usr/local/sbin/politsei-uuenda.sh`): it only ever deploys the current tip of `origin/main`
   (whatever the ticket says), fetches that commit, checks on the GitHub API that every
   check run of that commit succeeded, builds the frontend in a `node:22` container, copies the result
   into `www/` (contents, not the folder: bind mounts point to the inode), writes `version.txt`, checks
   `/api/health`, and restores the previous version if anything fails. After a successful switch it
   rebuilds the map data (section 2.1) when needed; that step can never fail or roll back the update.
5. `politsei-uuenda.timer` runs the same script every 10 minutes as a fallback (compares the deployed
   commit with `git ls-remote origin main`), so a missed webhook only delays an update.
6. When `/etc/pidu.env` provides a Telegram token and chat id, the script reports the result there.
